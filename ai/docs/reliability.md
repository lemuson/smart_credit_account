# Надёжность RabbitMQ

AI Service использует at-least-once delivery. Exactly-once выполнение не заявляется: publisher
confirm подтверждает приём публикации брокером, но сбой между публикацией результата и ack входного
сообщения способен привести к повторной обработке. Поэтому Main Backend обязан дедуплицировать
результаты по `request_id`.

## Топология

- `ai.events` — основной durable direct exchange.
- `ai.chat.request` — durable очередь запросов, dead-lettered в `ai.dlx`.
- `ai.chat.result` — durable очередь результатов, которую объявляет Main Backend/consumer.
- `ai.retry` — durable exchange и TTL-очередь `ai.chat.retry`; после задержки сообщение возвращается
  в `ai.events` с routing key `ai.chat.request`.
- `ai.dlx` и `ai.chat.dead` — конечная dead-letter точка.

Публикации persistent, publisher confirms включены, prefetch равен 1. `AI_WORKER_CONCURRENCY=1`
сохраняет порядок демонстрационного режима.

## Классы ошибок

- Невалидный envelope отклоняется средствами Pydantic/FastStream и не должен бесконечно
  возвращаться в основную очередь.
- Ошибка доступа или отсутствие ресурса не повторяются с изменёнными идентификаторами.
- Недоступность Ollama или Main Backend повторяется не более `RABBITMQ_MAX_ATTEMPTS` с задержкой.
- После исчерпания retry публикуется `failed` result со стабильным `error_code`, затем запрос ack.
- Неизвестное исключение приводит к reject без requeue; RabbitMQ направляет исходное сообщение в
  DLQ. Это сохраняет payload для разбора и исключает горячий цикл.

## Сбойные сценарии

| Сбой | Наблюдаемое поведение | Обязанность интеграции |
|---|---|---|
| Worker умер до ack | RabbitMQ доставит запрос повторно | Дедупликация результата |
| Worker умер после публикации результата до ack | Возможны два результата | Уникальный `request_id` |
| Ollama недоступна | Ограниченный delayed retry, затем failed | Показать безопасную ошибку |
| Backend вернул 403/404 | Нет перебора идентификаторов | Аудит попытки без утечки данных |
| RabbitMQ недоступен при publish | Исходное сообщение не ack | Повторная доставка после reconnect |
| Невалидный JSON/schema | Сообщение не обрабатывается как чат | DLQ и метрика invalid_message |
| Consumer результата недоступен | Durable очередь хранит результат | Контроль глубины очереди |

## Масштабирование

Глобальная concurrency 1 допустима для MVP. При нескольких worker сообщения одной беседы могут
обрабатываться параллельно. До масштабирования требуется последовательность по `conversation_id`:
consistent-hash exchange, partitioned queues либо распределённая блокировка с sequence number.
Встроенный ChromaDB также нужно заменить на общий сетевой сервис или обеспечить единственного
владельца файлового хранилища.
