# Умный кредитный кабинет предпринимателя — backend

Демонстрационный FastAPI-сервис для полного кредитного цикла малого бизнеса.
Python 3.13+, FastAPI, PostgreSQL 17, psycopg 3, SQLAlchemy 2, Alembic, JWT (HS256), Argon2.

## Запуск в Docker

```bash
cd backend
# Только при первой настройке, если .env ещё не существует:
cp .env.example .env
# Запишите в POSTGRES_PASSWORD и JWT_SECRET два разных случайных секрета:
python3 -c 'import secrets; print(secrets.token_urlsafe(48))'

docker compose up --build -d
# Пользователи и базовые данные создаются автоматически.
```

На текущем рабочем месте `.env` уже создан с независимыми случайными секретами;
он исключён из Git и Docker build context. Не перезаписывайте существующий `.env`.
Образ собирается в несколько стадий из `python:3.13-slim-bookworm`; зависимости
устанавливаются через `uv sync --frozen`. В runtime нет dev-зависимостей,
API работает от пользователя `credit` (UID 10001), доступен healthcheck.

Compose запускает `db` → одноразовый `migrate` (`alembic upgrade head`) → `seed-data` → `api`.
API стартует после готовности PostgreSQL, успешных миграций и загрузки базовых данных.
Swagger UI: `http://127.0.0.1:8000/docs`, OpenAPI: `/openapi.json`, готовность БД: `/health`.
Порт API можно изменить через `API_PORT` в `.env`. PostgreSQL доступен только
во внутренней сети Compose; его порт наружу не публикуется.

```bash
docker compose ps
docker compose logs --tail=100 api migrate
docker compose stop
docker compose start
```

Данные PostgreSQL хранятся в постоянном volume `smart-credit_postgres_data`.
Пересоздание контейнеров и `docker compose down` не удаляют volume.
Переменные `POSTGRES_USER/DB/PASSWORD` инициализируют новую БД; изменение `.env`
не меняет пароль и пользователей уже существующего PostgreSQL volume.
При первом запуске `seed-data` создаёт три продукта, клиента с профилем компании
и черновиком заявки, кредитного сотрудника и администратора.
Логины: `client@example.com`, `officer@example.com`, `admin@example.com`;
общий тестовый пароль: `Demo-credit-123!` (только локальный учебный стенд).
Отметка `demo-data-v1` в `seed_runs` предотвращает повторную загрузку, в том числе
при параллельном запуске. Данные и отметка фиксируются одной транзакцией;
после ошибки всё откатывается, загрузку можно повторить. Существующие учётные записи
и одноимённые продукты не перезаписываются. Профиль и черновик добавляются только
новому демо-клиенту. После успешной загрузки изменения и удаления сохраняются.
Команда вручную: `docker compose run --rm seed-data` (повторный запуск пропустит загрузку).
Прежняя команда `seed-products` сохранена для совместимости.

## Запуск без Docker

Нужен доступный PostgreSQL с отдельной БД и правами на создание таблиц.
В `.env` укажите `POSTGRES_HOST`, `POSTGRES_PORT`, `POSTGRES_DB`, `POSTGRES_USER`,
`POSTGRES_PASSWORD` либо полный `DATABASE_URL=postgresql+psycopg://...`.
Полный DSN имеет приоритет **при локальном запуске**; пароли внутри него должны
быть URL-encoded. При использовании отдельных `POSTGRES_*` кодирование выполняется
автоматически. Compose всегда использует собственный `db` и отдельные `POSTGRES_*`.

```bash
# Из каталога backend:
uv sync --locked
uv run alembic upgrade head
uv run python -m app.cli seed-data
uv run uvicorn main:app --reload
```

Существующие SQLite-файлы не удаляются и не переносятся автоматически. При наличии
реальных данных потребуется отдельная согласованная выгрузка/загрузка; запуск
PostgreSQL создаёт новую БД. SQLite оставлена только как явно выбираемый механизм
быстрых автономных тестов, настройки по умолчанию используют PostgreSQL.

## Модули и хранение

В `app/auth`, `profiles`, `products`, `applications`, `loans`, `risk`, `feed` находятся
`models.py`, `dao.py`, `service.py`, `router.py`, `schemas.py`. HTTP-совместимость
каталога реализована в `app/catalog.py`. Контроллеры используют сервисы;
DAO работают с SQLAlchemy Session. Синхронные SQL/Argon2/файловые операции выполняются
FastAPI в пуле потоков. Успех возвращается после commit транзакции.

Таблицы: пользователи, профили компаний, продукты, заявки, документы, проверки,
уточнения, аудит переходов, кредиты, текущая риск-политика, история её версий и отметки загрузки базовых данных.
Все данные сохраняются между перезапусками. Основное хранилище — PostgreSQL 17.
Миграции создают таблицы в порядке зависимостей; циклический внешний ключ
`loans.application_id → applications.id` добавляется после создания обеих таблиц.
При откате этот ключ удаляется перед таблицами. Исходная миграция исправлена для
первого развёртывания PostgreSQL; последующие ревизии Alembic сохранены.

Тенант MVP — один клиент и один профиль компании. Несколько сотрудников организации,
корпоративные полномочия и мультиорганизационный доступ не реализованы. КМ видят
поданные заявки банка, изменять первичную обработку может только назначенный КМ.
Черновики доступны только их владельцу. Системный администратор управляет учётными
записями, продуктами и риск-правилами.

## Авторизация и API

Базовый префикс `/api/v1`. Во всех защищённых запросах:
`Authorization: Bearer <access_token>`. Роли: `CLIENT`, `BANK_OFFICER`, `ADMIN`.
Публичная регистрация создаёт только клиента; поле `role` в ней запрещено.
Сотрудник создаётся через CLI или `POST /admin/users` администратором.
JWT имеет срок действия и проверяет issuer/audience; отключение пользователя немедленно
блокирует его существующий токен. Заголовки `X-User-ID`/`X-Organization-ID` не используются
для авторизации. Пароли хешируются Argon2; секрет JWT обязателен, минимум 32 символа.

| Контур | Маршруты |
| --- | --- |
| Авторизация | `POST /auth/register`, `POST /auth/login`, `GET /auth/me` |
| Компания | `GET /auth/company/suggest/{inn}`, `POST /auth/company`, `GET/PUT /profile` |
| Каталог | `GET /catalog/products`, `POST /catalog/calculate-preview` |
| Продукты | `GET/POST /credit-products`, `GET/PUT /credit-products/{id}`, `GET /credit-products/search`, `GET /credit-products/{id}/required-documents` |
| Черновик | `POST/GET /client/applications`, `GET/PUT /client/applications/{id}` |
| Документы | `POST /client/applications/{id}/documents`, `GET/DELETE /client/applications/{id}/documents/{doc_id}` |
| Подача и уточнения | `POST .../{id}/submit`, `GET .../{id}/clarification`, `POST .../{id}/clarify` |
| Оффер и оформление | `GET .../{id}/offer`, `POST .../{id}/offer/accept`, `POST .../{id}/offer/decline`, `GET .../{id}/contract`, `POST .../{id}/sign` |
| КМ | `GET /bank/applications/queue`, `GET /bank/applications/{id}/dossier`, `GET /bank/applications/{id}/documents/{doc_id}` |
| Обработка | `POST /bank/applications/{id}/take-to-work`, `.../run-external-checks`, `.../request-clarification`, `.../reject-primary`, `.../pass-to-auto-analysis` |
| История кредитов | `GET /client/loans`, `GET /client/loans/{id}`, `POST /bank/loans/import` |
| Администрирование | `POST /admin/users`, `PATCH /admin/users/{id}`, `GET/PUT /admin/risk-policy`, `GET /admin/risk-policy/history` |
| Лента | `GET /client/feed` |
| Совместимые read-only API | `GET /applications/{id}/status`, `POST /applications/{id}/validate` |

Поиск продуктов: `purpose`, `amount`, `term_months`; цели:
`working_capital`, `equipment`, `expansion`, `refinancing`.
Каталог фильтруется по цели, сумме и сроку; соответствие возрасту бизнеса,
выручке, залогу и риску проверяется при автоматическом анализе.
Списки поддерживают `offset` и `limit` (1–100). Очередь и список заявок — фильтр `status`.
`GET /auth/me` возвращает пользователя и известные компании.

Все изменения заявки требуют `expected_version` из последнего GET или ответа операции.
Для загрузки это поле multipart, для удаления — query parameter, для остальных операций — JSON.
После загрузки/удаления документа или запуска проверок перечитайте заявку/досье для новой версии.
Устаревшая версия даёт `409 APPLICATION_VERSION_CONFLICT`. SQLAlchemy дополнительно
проверяет версию в UPDATE, предотвращая гонки между чтением и записью. Уникальная связь
кредита с заявкой и конечное состояние защищают от повторной выдачи.

Ошибки имеют `detail.code` и при необходимости `detail.errors`.
Типичные коды: `APPLICATION_INVALID`, `INVALID_APPLICATION_STATE`,
`FRESH_EXTERNAL_CHECKS_REQUIRED`, `UNRESOLVED_DISCREPANCIES`, `INVALID_SIGNING_CODE`.
Чужой и отсутствующий объект одинаково возвращают 404. Валидационные ошибки
не отражают обратно входные пароли или полные анкеты. Ответы имеют `Cache-Control: no-store`.

## Жизненный цикл

```text
DRAFT → SUBMITTED → PRIMARY_REVIEW → AUTOMATIC_ANALYSIS → OFFER_READY
                      ↕                   ↓                  ├→ OFFER_DECLINED
               NEEDS_CLARIFICATION       REJECTED             ↓
                      └→ PRIMARY_REVIEW               OFFER_ACCEPTED → SIGNING → DISBURSED
```

КМ также может отклонить заявку из `PRIMARY_REVIEW` с обоснованием.
Клиент редактирует данные и документы только в `DRAFT` и `NEEDS_CLARIFICATION`.
Подача и уточнение требуют `confirmed: true`, полного профиля, финансов и документов.
Заявка без обязательных документов остаётся черновиком. КМ может запросить дополнительные
виды документов или уточнение уже представленных сведений. Запросы и ответы видны
в досье, а активный дозапрос отображается в ленте кабинета.

Уточнение возвращает заявку **сразу в PRIMARY_REVIEW** прежнему КМ. Каждое изменение
анкеты/документов и ответ клиента увеличивают `data_revision`; старые проверки
не подходят для запуска анализа. Проверки сохраняются с этой ревизией. Анализ
также обнаруживает изменения истории действующих кредитов после проверки.

Автоанализ синхронный: промежуточный `AUTOMATIC_ANALYSIS` и итоговое состояние
сохраняются в одной транзакции вместе с аудитом. Клиент сразу получает итоговый
результат, отдельного брокера/фонового worker для этих небольших расчётов нет.
Принятие оффера аналогично сохраняет `OFFER_ACCEPTED` и `SIGNING` в истории,
формируя договор в одном запросе. Договор — структурированный JSON с условиями,
анкетой и SHA-256; PDF/DOCX и настоящая электронная подпись не формируются.

Для демо-подписания передайте `code: "123456"` и `contract_sha256` из договора.
Срок кода — 15 минут, максимум 5 ошибочных попыток; счётчик сохраняется даже при
HTTP-ошибке. Автоматического перевыпуска кода нет. Договор и история содержат
признак `demonstration_only`. `DISBURSED` означает учебную фиксацию выдачи,
банковского перевода средств нет.

## Анкета и повторный кредит

`company`: `name`, `inn` (10/12 цифр с проверкой контрольных разрядов),
`registration_date` (не в будущем), `address`, `industry` (код ОКВЭД для ленты).

`financials`: `annual_revenue`, `monthly_expenses`, `monthly_debt_payments`,
`outstanding_debt`, `credit_history` (`good/average/bad/none`), `overdue_days`, `has_collateral`.
Денежные значения передавайте десятичными строками, не float. В ответах они также строки.
Значения неотрицательны, выручка строго положительна, точность сумм — копейки.
`monthly_expenses` — операционные расходы без кредитных платежей.

Создание черновика копирует профиль. Если передан `source_loan_id`, отсутствующие
поля дополняются снимком старого кредита этого же клиента; без ID автоматически
используется последний известный кредит. Свежий профиль имеет приоритет.
Финансовые сведения из истории — подсказка: клиент обязан проверить их актуальность.
Платежи и остатки действующих локальных кредитов задают нижнюю границу обязательств.
Занижение при ручной правке выявляется проверками и блокирует автоанализ до уточнения.
Документы из старых заявок не копируются, их нужно загрузить заново.

Исторические кредиты импортируются КМ через `/bank/loans/import`: клиент, внешний
уникальный номер `external_reference`, сумма, остаток, платёж, ставка, срок,
`active/closed`, просрочка, снимки компании и финансов. Новая демо-выдача автоматически
попадает в историю. Погашения и обслуживание кредита после выдачи в этот MVP не входят.

## Документы и внешние проверки

Документы хранятся в БД вместе с метаданными и SHA-256. Поддерживаются PDF/PNG/JPEG,
проверяются MIME и начальная сигнатура, размер до 10 МБ (настраивается), до 20 файлов
на заявку. Виды: `registration`, `financial_statements`, `bank_statement`, `collateral`.
Скачивание всегда с `Content-Disposition: attachment` и проверкой прав.
Проверка подлинности, антивирус и извлечение содержимого не реализованы.

Симуляторы не обращаются во внешние сервисы. Последние две цифры корректного ИНН:

| Окончание | ФНС | БКИ | Тестовый ИНН |
| --- | --- | --- | --- |
| `01–79` | Действует, долгов нет | 4 закрытых кредита без просрочек | `7700000009` |
| `80–89` | Налоговый долг 18 500 | 2 закрытых кредита, задержка 3 дня | `7700000087` |
| `90–99` | Ликвидация, счета заблокированы | Текущая и историческая просрочка 90 дней | `7700000094` |

Неописанное в ТЗ окончание `00` трактуется как стабильная компания.
Дата регистрации берётся из анкеты; совпадение руководителя — синтетический результат,
идентичность руководителя действительно не проверяется. БКИ учитывает также локальные
действующие кредиты; противоречия сохраняются отдельно. Данные `credit_history`
клиента не подменяют результаты источника при расчёте дисциплины.

## Решение и финансовые расчёты

Исходная политика соответствует ТЗ: база 500, диапазон 300–850; факторы срока работы,
выручки к кредиту, рентабельности, дисциплины БКИ и налогов. В неоднозначных строках
таблицы выбраны границы: ≥36 месяцев — +60, выручка ≥5 сумм — +80,
≥3 закрытых кредитов без просрочек — +100. Исторические задержки 11–29 дней дают 0,
30–89 дней — −100, 90+ — стоп-фактор. Симуляторы выдают только 0, 3 или 90 дней.
При стоп-факторе отказ обязателен независимо от итогового балла.

Возраст бизнеса <6 месяцев, недействующий статус, блокировка счетов, текущая просрочка
>30 дней и историческая ≥90 приводят к отказу. Дополнительно проверяются выручка,
обеспечение и возраст из условий продукта, положительная чистая прибыль.

ПДН = (текущие платежи + новый аннуитетный платёж) / среднемесячная чистая прибыль.
A ≥750: базовая ставка; B ≥650: +1,5 п.п.; C ≥550: +3,5 п.п. и 70% суммы;
ниже — отказ. ПДН >50% добавляет ещё 1,5 п.п., после чего нагрузка пересчитывается.
При ПДН >70% категория A получает снижение лимита до ПДН ≤65%; для B/C — отказ.
Более строгий лимит ПДН продукта сохраняется. Если сниженная сумма ниже минимума
продукта или нагрузку нельзя привести к пределу, формируется отказ.

Суммы/ставки/график считаются `Decimal`, округление — `ROUND_HALF_UP` до копеек.
В PostgreSQL суммы и ставки хранятся как `NUMERIC(18,2)`, лимиты ПДН — `NUMERIC(18,4)`,
даты — `TIMESTAMPTZ` с нормализацией в UTC. Python использует `Decimal` без преобразования
в float. В автономных SQLite-тестах тот же тип сохраняет целые единицы с масштабом.
Последний платёж корректирует остаток основного долга. Даты — календарные месяцы
с сохранением дня по возможности; для 31 января следующая дата — конец февраля.
Сохраняются балл, категория, вклады факторов, метрики, причины отказа, версия
и полный снимок применённой риск-политики. Условия продукта фиксируются в черновике;
изменение справочника не переписывает существующие заявки. Неактивный продукт нельзя
выбрать или подать по нему новый черновик.

`ADMIN` может менять веса, пороги категорий, надбавки, допустимую нагрузку и коэффициент
лимита через `/admin/risk-policy`, используя `expected_version` (изначально 0).
Пороговые значения проверяются на согласованность; правки хранятся с автором и версией.
Они влияют только на последующие анализы, готовые решения не пересчитываются.

## Проверка и ручные сценарии

```bash
uv run pytest -q
uv run ruff check app tests examples migrations main.py
uv run ruff format --check app tests examples migrations main.py
docker compose exec api alembic check
```

41 автоматизированный тест: API-сценарии выдачи, уточнения, отказа по стоп-факторам,
отказа клиента, отказа КМ; ACL, JWT, документы, версии, гонка КМ, демо-ПЭП,
старый кредит, администрирование, риск-политики, аннуитеты и границы правил.
По умолчанию тесты создают изолированные SQLite-БД для запуска без инфраструктуры.
Для проверки на **настоящем PostgreSQL**:

```bash
docker compose --profile test run --build --rm tests
```

Тестовый образ содержит dev-зависимости и запускает весь pytest-набор, затем реальный
HTTP-сценарий Uvicorn. Каждый тест создаёт отдельную случайную схему `credit_test_*`:
`upgrade → check → downgrade → upgrade → check`. После теста удаляется только его схема;
рабочие таблицы и данные схемы `public` не затрагиваются. Нужны права `CREATE` схем
в тестовой БД. Без Docker можно задать `TEST_DATABASE_URL` отдельной PostgreSQL БД
и выполнить `uv run pytest -q`; при `TEST_POSTGRES=1` используются настройки `POSTGRES_*`.
Тесты проверяют в том числе точность больших сумм, timezone и конфигурацию паролей.

Дополнительный smoke-запуск: `uv run python -m examples.http_smoke`.
Он также поддерживает `TEST_DATABASE_URL`/`TEST_POSTGRES=1`, использует изолированную
БД/схему и автоматически останавливает свой сервер.

Интерактивная коллекция: `examples/credit-flow.http` (JetBrains HTTP Client),
рядом `demo.pdf` — синтетическое вложение. Запросы 1–27 — happy path; ветки

на ingress, аудит административных учётных записей и реальные провайдеры проверок/подписи.

## Интеграция AI Service

Полный кабинет с AI запускается `./start.sh` из корня. Backend отдельно сохраняет прежний режим:
чат по умолчанию отключён (`AI_ENABLED=false`). Для локального подключения задайте `AI_ENABLED=true`,
`AI_SERVICE_TOKEN`, `RABBITMQ_URL` и отдельно запустите `uv run python -m app.ai.worker`.
AI Service получает тот же `BACKEND_SERVICE_TOKEN`, URL backend и `BACKEND_CONTRACT=main`.

Пользовательский API (роль CLIENT, обычный Bearer):

- `POST /api/v1/chat/conversations` → `201`, `conversation_id`.
- `POST /api/v1/chat/conversations/{conversation_id}/messages` с
  `{"request_id":"<UUID>","message":"Текст","application_id":null}` → `202`.
- `GET /api/v1/chat/requests/{request_id}` → `pending`, `published` или конечный AI-статус
  и `result` с `answer`, `sources`, `suggested_actions`.
- `GET /api/v1/chat/conversations/{conversation_id}/messages` → последние 100 запросов с ответами.

`request_id` создаёт клиент один раз на логический запрос и повторно использует при сетевом сбое.
Та же key с другим содержимым даёт 409; второй активный запрос в диалоге — 409.
Лимит — 10 новых запросов в минуту на пользователя (429). Повтор существующего запроса лимит не расходует.
`user_id` берётся из авторизации, `organization_id` — ID принадлежащего клиенту профиля компании.
В MVP один профиль на клиента; произвольные identity-поля в теле запрещены.

Миграция `a18f210c9021` добавляет `ai_conversations` и `ai_chat_jobs`. Запись job служит outbox;
результат в той же строке — inbox с уникальным `request_id`. Статус и ответ фиксируются атомарно;
первый результат выигрывает, повтор не создаёт нового сообщения. Частичный уникальный индекс
запрещает два активных job на диалог. После publisher confirm job помечается `published`.
При сбое брокера pending сохраняется; опубликованные запросы без ответа повторяются через 5 минут
с прежним ID. Доставка at-least-once, повторная генерация со стороны AI возможна.
Результат подтверждается только после commit/no-op; malformed/неизвестные результаты отклоняются
без requeue, временная ошибка хранения — с requeue. Очередь результата создаётся до публикации.

В durable сообщение попадает отдельный JWT делегирования на 10 минут с audience
`smart-credit-ai-tools`, привязанный к пользователю, профилю и job. Он создаётся заново при повторной
публикации; пользовательский access token не сохраняется и не публикуется. Доступ разрешён только
к шести read-only tool-маршрутам при правильном `X-Service-Token` и совпадении подписанного контекста,
проверенных заголовков и текущей job в БД. После сохранения результата делегирование недействительно.
Чужие заявки/диалоги возвращают 404. Обычные пользовательские токены сохраняют прежний доступ.

Форматы существующих HTTP-ответов сохранены. Поиск продуктов теперь допускает незаданные фильтры;
для AI дополнительно проверяются возраст бизнеса, выручка, наличие залога и, при известных сумме/сроке,
долговая нагрузка. AI adapter переводит эти ответы в формат инструментов. RabbitMQ envelope остаётся 1.0.
Согласование изменения envelope не требуется; production identity/TLS/раздельные RabbitMQ-права
нужно настроить отдельно, локальный shared secret не заменяет workload identity.

Проверки:

```sh
uv run pytest -q
# Только изолированный тестовый RabbitMQ; тест использует стандартные ai.* очереди:
TEST_RABBITMQ_URL=amqp://guest:guest@localhost:5678/ uv run pytest -q tests/test_ai.py
```

Тест RabbitMQ проверяет реальную доставку и сохранение с повтором результата, но не запускает LLM.
Полный генеративный E2E требует доступного AI worker, Ollama и установленных моделей.
